# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Sheafly is a Microsoft Project–style scheduling app for macOS, Windows and Linux, built with Tauri 2, React 19, and Rust. The UI is in Vietnamese and English (see Languages below). `README.md` is in English and `README.vi.md` in Vietnamese; keep them in step. The plan doc is in Vietnamese.

## Commands

```bash
pnpm install
pnpm tauri dev                          # run the desktop app (Vite on :1420 + Rust shell)
pnpm build                              # tsc + vite build (frontend only)
pnpm exec tsc --noEmit                  # typecheck
pnpm test                               # frontend tests (Vitest, jsdom)
pnpm test src/viewRows.test.ts          # a single frontend test file (add -t "<name>" for one case)
cargo test -p sheafly-engine        # engine tests
cargo test -p sheafly-license       # license keys (CI also runs `--release --test license`: release builds refuse the dev key)
cargo run -p sheafly-license --features issue --bin sheafly-keygen -- issue --dev --name Lan --email lan@example.com  # a Pro key for `pnpm tauri dev`
cargo test -p sheafly-engine <name> # engine tests whose name matches the filter
cargo bench -p sheafly-engine --bench large_project            # apply/undo/save/open timings, 1,000 tasks and 10,000 commands
cargo bench -p sheafly-engine --bench large_project -- 300 1200  # same with <tasks> <commands>
cargo bench -p sheafly-engine --bench large_project -- leveling   # leveling 500 tasks on 10 people
cargo bench -p sheafly-engine --bench large_project -- capacity 500 5000  # leveling a sprint backlog: <people> <tasks>
cargo bench -p sheafly-engine --bench large_project -- suggest 500 5000   # assignment suggestions: <people> <tasks>
cargo bench -p sheafly-engine --bench large_project -- capacity 500 5000 interrupt  # leveling with 5% urgent tasks
cargo bench -p sheafly-engine --bench large_project -- capacity 500 5000 linked  # leveling with finish-to-start chains
cargo bench -p sheafly-engine --bench large_project -- import 5000   # check_import and ImportRows for 500 people, 5000 tasks
cargo bench -p sheafly-engine --bench large_project -- loadmap 500 5000  # load_map for a year by week and twelve weeks by day
cargo bench -p sheafly-engine --bench large_project -- forecast 500 5000 1000  # finish forecast: <people> <tasks> <runs>
```

Measure speed with these benches (release), never in a test: under `cfg(test)` leveling also checks every quick reschedule against a full pass (`ripple.rs` `same_as_full_pass`), which makes a linked 5,000-task leveling look a hundred times slower.

The webview runs under a CSP (`app.security.csp` in `tauri.conf.json`): scripts only from the app, inline styles allowed (components use `style={…}`), images and fonts also from `data:`/`blob:` (canvas and jsPDF). A new feature that loads anything else (a remote font, `eval`, a worker) needs the policy widened, and checked against the production build. CI (`.github/workflows/ci.yml`) runs the engine tests, the typecheck, and `pnpm test`. `.github/workflows/build.yml` builds installers for macOS (universal: Apple Silicon and Intel), Windows, and Linux, then a `checksums` job writes `SHA256SUMS.txt` (attached to the draft release on tags). It runs on `v*` tags, which also create a draft release, and on manual dispatch, never on ordinary PRs or pushes. The macOS app is signed with a Developer ID, notarized and stapled only when all six Apple secrets are set (`docs/release-signing.md`; a step exports them for the Tauri CLI, whose `APPLE_SIGNING_IDENTITY` overrides the config); with none it keeps the ad-hoc signature (`bundle.macOS.signingIdentity "-"`), and with only some the job fails. The release text follows. A check step mounts the `.dmg` and always requires `x86_64` and `arm64` from `lipo -archs`, plus `codesign --verify --strict --deep`, `spctl` (notarized Developer ID) and `stapler validate` when signed. Windows and Linux are not signed. The real UI only works inside Tauri: `inTauri()` guards every `invoke`, so a plain browser at `localhost:1420` can't load project state.

## Architecture

Cargo workspace with three members: `crates/engine` (pure Rust, no Tauri dependency), `crates/license` (Sheafly Pro license keys) and `src-tauri` (thin IPC shell). The React app lives in `src/`.

**The engine is the source of truth.** The UI never computes dates, slack, the critical path, costs, EVM, or burn-down numbers. It sends a `Command` and renders the `Snapshot` it gets back.

- **Time model** (`crates/engine/src/lib.rs`, `timeutil.rs`): instants are Unix milliseconds holding *project wall-clock time* formatted as UTC (no timezone conversion). Durations, lags, and work are **working minutes**. `Calendar` converts between the two.
- **Command log and undo** (`command.rs`, `document.rs`): every edit is a variant of the serde-tagged `Command` enum (`#[serde(tag = "type", rename_all = "snake_case")]`). `Document::apply` runs `apply_one` on a clone, then `schedule()`, and commits only if both succeed. Undo and redo **replay** `base` plus `commands[..cursor]` instead of reversing anything, so every command must be deterministic and replayable from the base project.
- **Checkpoints** (`checkpoint.rs`): `Document::project_at` replays from the nearest cached scheduled state instead of from `base`. `apply` and replays keep one every `INTERVAL` (25) commands; memory holds at most 24, dense near the present with sparse anchors further back. A checkpoint is only a cache: `apply` drops the ones past the cursor when it truncates the log. Files store the checkpoint at the cursor plus three below it, tagged with `engine_tag()` (crate version plus `ENGINE_REVISION`); `load` uses only matching ones and replays otherwise. **Bump `ENGINE_REVISION` whenever an engine change can move dates or derived fields for the same commands.**
- **Scheduling** (`schedule.rs`): `schedule()` runs after every command. It normalizes the outline/WBS, builds a `Graph` (`graph.rs`: UID → position, subtrees, links per task, leaf order; a link to or from a summary goes through one virtual node instead of every leaf pair), which also detects cycles, runs forward/backward CPM passes (with a few passes for summary finish constraints), then rolls up summaries and publishes derived fields: free slack, costs and usage (`work.rs`), overallocations (`level.rs`), predecessor text, and the late flag. Derived fields live on the model structs and are overwritten on every schedule run.
- **Persistence** (`store.rs`): a `.sheafly` file (`.pdproj` before the rename from ProjectDesk; both open, saves default to `.sheafly`) is SQLite with `meta` (version, cursor, base project JSON), `command_log` (serialized commands), and `burndown`. On load (`store::open`) the engine replays the log from the nearest checkpoint. A command that does not parse, is unknown (likely from a newer app), or fails to apply does not stop the open: `open` returns an unsaved copy (`path` None, `dirty`) at the last state it can rebuild (a later checkpoint this engine saved, else the replayed prefix with its undo history), Damage only in the redo commands after the cursor opens the file itself and drops those commands on the next save. A damaged cursor or burn-down table also opens. `open` returns an `OpenReport` (`recovery.rs`) whose `message()` the Tauri layer shows as a warning sheet. The report also lists tasks whose dates differ from a checkpoint another engine saved at the cursor. `load` is `open` without the report. Burn-down snapshots sit outside the command log on purpose, so undo doesn't remove them. `save` writes a new, uniquely named hidden temp file beside the real file (following a symlink) in one transaction, keeps the old file's permissions, and renames it over the file, so a crash never leaves a half-written project. `load` refuses files whose `version` is above `FORMAT_VERSION`. **Bump `FORMAT_VERSION` whenever you add a `Command` variant or a table an older app must read**, because an older app replaying the log cannot read commands it doesn't know. The `checkpoint` table is a cache older apps ignore, so it did not need a bump.
- **Autosave and history** (`autosave.rs`, `Document::compact_history`): a background thread in the Tauri layer writes unsaved changes every 30 s to one slot in the app data folder (`autosave.pdproj` plus a JSON note naming the original file). Saving, discarding, replacing the document, or quitting clears it. On launch the frontend calls `check_autosave`, which offers the slot back; a restored project is unsaved changes to its original path. "Gộp lịch sử hoàn tác" (`compact_history`) folds all but the last 100 undo steps into `base`; it is not a `Command` and cannot be undone.
- **Work weeks** (`calendar.rs`): besides the default `week`, a `Calendar` has `work_weeks`, each a name, an inclusive `[from, to]` span and its own seven days (`SetCalendarWorkWeek` replaces the one that starts on `from`; `ClearCalendarWorkWeek`). They never overlap (`Invalid::WorkWeekOverlaps`). The hours for a date come from its exception, else the work week that covers it, else the default week, via `ranges_on`/`week_for`; read the week through those, never `calendar.week` directly (the frontend's `ganttKeys.ts` does the same). With work weeks, `add_working` loses its whole-week skip and `full_days_between` splits the span at the work week edges (`pattern_minutes`), so cost stays proportional to the number of work weeks, not days. MSPDI reads and writes `<WorkWeeks>` (`mspdi_workweeks.rs`); an overlapping one in a file is dropped. Calendar exceptions come from `<Exceptions>` and from a `<WeekDay>` with `DayType` 0 (what Project 2003 writes: `TimePeriod`, `DayWorking`, `WorkingTimes`); both go through `mspdi_calendar_days::add_exception` into `Calendar.exceptions`, and one with no `FromDate` is dropped with an `ImportNote`. Export writes only `<Exceptions>`.
- **Base calendars** (`calendar_base.rs`): a calendar can be based on another (`SetCalendarBase`, or `CreateCalendar { base_id }`, which the app uses for new task and resource calendars). `Calendar.base` holds only what it sets itself (weekdays, exceptions, work weeks); `refresh`, run in `schedule::prepare`, writes base plus own into the calendar's ordinary fields, bases first, so the scheduler never follows bases and a project holiday reaches every calendar based on it. Edits act on those merged fields and `after_edit` (from `apply_one`, also for `AddHoliday`/`RemoveHoliday` on the project calendar) keeps what differs from the base as its own; a day equal to the base's follows the base. An inherited exception or work week cannot be removed on the based calendar (`Invalid::InheritedFromBase`), only overridden; a work week it sets drops the inherited ones it overlaps. Bases never loop (`CalendarBaseLoop`); a loop or missing base in a file leaves the calendar standing alone. MSPDI writes `IsBaseCalendar` 0, `BaseCalendarUID` and only the own part.
- **Actual costs** (`work.rs` `compute_costs`): computed from progress by default. With `Project::editable_actual_costs` on (`SetEditableActualCosts`), a task's `manual_actual_cost` (`SetTaskActualCost`; empty goes back to computed) replaces the computed actual cost, its labour share is spread over its assignments, and remaining cost is cost minus actual. An assignment can have its own entry too (`SetAssignmentActualCost`): it replaces that assignment's computed share and the task total becomes the fixed-cost actual plus its assignments, unless the task has an entry of its own, which wins (the assignments then share it). Entries are kept when the switch is turned off; a summary rolls up its children, and an occurrence with an entry (on the task or an assignment) counts as having progress for its series. `evm::actual_cost_at` spreads an entered cost over the task's progress windows, or books it on the status date when the task has no progress. MSPDI import keeps a file's `ActualCost` as an entry only where it differs from the computed value (`keep_real_entries`), assignments first; a resource's actual cost is always the sum of its assignments, and there is no entry over time.
- **Overallocation and leveling** (`level.rs`): a resource is overallocated when, at some instant, the units of the assignments working then exceed what it has (while its calendar works, its units that day, else none). The units of a day come from `availability.rs`: `Resource.availability` periods (inclusive dates, either end open; set by `SetResourceAvailability`, kept sorted and apart) override `max_units` on their days, outside them the resource has its max units (Project instead has it away outside its availability table). Only overallocation and leveling read them, never durations or work; work counts only inside the task calendar's ranges and segments, so tasks at different hours of one day do not clash. Leveling is serial: tasks it cannot move (manual, started, MSO/MFO) first, then tasks whose leaf predecessors are placed, then the project's leveling order (`level_order.rs`: `Project.leveling_order`, set by `SetLevelingOrder`, up to 8 criteria among start, priority, slack, deadline, duration, ID and custom fields, each ascending or descending, a missing value always last; empty means the default, earliest start, higher priority, less slack, the slack before leveling so the order does not depend on what was placed), then the uid; `DeleteField` drops its criterion, changing the order does not re-level, and only `.sheafly` files keep it (MSPDI has no element for it; an import resets it). Each task goes to the first moment all its resources have room, and placed tasks never move again. A task needing more units than a resource will ever have from its start on skips that resource; `room_from` passes a period without enough units (a leave) in one go (`Capacity::next_with`). A task whose calendar works hours a resource never covers is left where it was: `earliest_fit` stops once the search, past the placed work and the calendars' last exception or work week and the capacities' last change, returns to a start at the same point of the week (`Cycle` in `level_cycle.rs`), which can never fit; results are the same as searching the full four years. `schedule()` is split into `prepare` (graph), `schedule_dates`, and `publish_derived`, so leveling builds the graph once and only reschedules dates. After each delay `ripple.rs` reschedules only the delayed task and the leaves its links reach, with the same `schedule_leaf`; a project with an ALAP task or a summary that must finish by an FF/SF link or an FNET/MFO date reschedules in full instead. A unit test in `ripple.rs` levels generated projects both ways and requires the same result, so a change to the forward pass must keep the two in step. `Document::apply` logs `LevelResources` as `ApplyLeveling { delays, splits }`, so replay never reruns the heuristic. **Urgent tasks** (`level_interrupt.rs`, a child module of `level.rs`; `Task.interrupts`, set by `SetInterrupts` on leaves only): when the project has one, leveling lets it go ahead of work in progress ranked below it on the people they share. "Ranked below" is the leveling order with the start left out (`Order::ranks_above`; a tie does not interrupt), since the default order puts the earlier start first. The urgent task is placed as if the load of such work were not there (keeping the part already done of started work), then each piece of that work it overlaps is split where it begins (`Split { leveling: true }`, the shortest gap that lets the rest fit, `gap_after`) or, when not running yet, delayed; an ordinary task placed after an urgent one ranked above it flows around its work (`fit_around`). Manual, MSO/MFO, priority 1000 and urgent work are never split, nor work started with nothing done. Each leveling run starts by removing the splits leveling made; Clear Leveling removes them too; `ApplyLeveling.splits` replays them per task, leaving the user's own splits alone. With no urgent task none of this runs, so leveling is unchanged. Only the people whose work moved have their load swept again. Placed work a split or delay pushes (a victim's successors) is placed again next to the load as it now is, down the links (`settle_moved`). Work that can neither pause nor wait (started, no gap fits) keeps its place and the urgent task goes after it. The searches stop two weeks past the last placed work, where only the calendars clash. A leveling pause dragged by hand (`MoveSegment`) becomes the user's; MSPDI writes leveling splits as ordinary ones and reads every split as the user's; a copy keeps the flag but not leveling's splits; `RescheduleUncompleted` measures without leveling's pauses. Fill-down takes the flag (`FillField::Interrupts`), skipping summaries and milestones.
- **Skills, assignment rules and suggestions** (`skills.rs`, `suggest.rs`): the project names skills (`Project.skills`, ids never reused via `next_skill_id`, at most 200, names unique letter case aside and without commas) and each resource holds some (`Resource.skills`, sorted ids; `SetResourceSkills`). Tasks have no skill of their own: `Project.assignment_rules` is an ordered list whose conditions read custom field values (all must hold, a value matches one of the listed ones, a task with no value does not match, no conditions matches every task) and whose target is one person or everyone with a skill, with the units to assign; the first matching rule wins (`rule_for`). `SetAssignmentRules` replaces the list (at most 200 rules of 8 conditions, values checked against the field, units above 0 and at most 1,000). The commands that change data keep the rules true: `DeleteField` drops every rule with a condition on the field, `UpdateField` converts and renames condition values as it does task values (a condition left empty drops its rule), and `DeleteResource`/`DeleteSkill` drop the rules pointing at them. `suggest::suggest` (Tauri read `suggest_assignments`, never logged) takes the unassigned leaves not started yet that are neither milestones nor occurrences of a series (assigning one would detach it) in the project's leveling order, tasks leveling would not move first; a task leveling would not move keeps its dates (an MFO task whose length the rule changes ends on its finish) and is offered only to people with room at them (`Loads::fits_at`). For each of the others, every candidate of the first matching rule is dated as if assigned at the rule's units (`work::with_first_assignment`, the same task-type table as `add_assignment`) and placed with leveling's search next to their load (`level::Loads` in `level_loads.rs`: capacity by date, calendars, four-year limit; a resource that never has the units gets no place). Candidates rank by finish, then less assigned work, then uid; at most 5 are kept, and the top one takes the task into its load before the next task (greedy), so a batch spreads over the people with the skill. Candidates are tried in the order of a lower bound (the finish from the first moment they have room, `Loads::earliest_room`) and the rest are skipped once they cannot do better; a unit test compares that with placing everyone on generated projects. A task with no pick says why (`NoPick`: no rule, nobody with the skill, no room). Links between suggested tasks are not followed; accepting sends `AssignTasks` (many rows, one undo step, each row as `AssignResource`, one bad row or an empty list fails), and leveling gives the real dates. Skills cross MSPDI as a resource text field (`mspdi_skills.rs`): export declares resource Text1 (`FieldID` 205520904) with the alias "Kỹ năng" and writes each resource's names comma-separated; import reads any resource text field aliased "Kỹ năng" or "Skills" (letter case aside) and makes a skill of each name. Rules stay in `.sheafly` files only. Project's generic resources are not used.
- **Skill levels and roles** (`skill_levels.rs`, capacity plan PR 1; issue #150): `Project.skill_levels` is an ordered scale, lowest first (ids never reused, `next_skill_level_id`, at most 20, names unique letter case aside, no comma or colon); empty means levels are not used. `Resource.skill_levels` maps a skill the resource has to a level; no level ranks below every level. `SetSkillLevels` replaces the scale (an entry with an id keeps that level, one without is new; a removed level's people and rules move to the nearest kept level below, else to none), `SetResourceSkills` takes `levels` (a list of `{ skill, level }`, absent in older logs; a map would not read inside the tagged `Command`), `DeleteSkill` drops the level with the skill. `RuleTarget::Skill.min_level` limits a rule to people at that level or above (`qualifies`), and suggestions follow it. `Resource.group` is a role or team label (`SetResourceGroup`, at most 100 characters); scheduling never reads it. Skill names may no longer hold a colon: MSPDI's skills field and table import write and read `Skill:Level` (`split_level`, last colon), adding a level the project lacks at the top of the scale in the order met. MSPDI writes the group as `<Group>`, or the kind ("Người"/"Máy") when there is none, as before; import reads a `<Group>` that only names a kind as no group. `FORMAT_VERSION` 23. UI: the scale (`SkillLevels.tsx`) and a level select per person and skill in Giao việc → Kỹ năng, "từ cấp" on a skill rule, the resource sheet's Vai trò column with a role filter, and a Vai trò column in table import (`group`).
- **Productivity factor** (`focus.rs`, capacity plan PR 2; issue #150): `Project.focus_factor` (0.5–1.0, default 1.0, `SetFocusFactor`) is the share of time at work people give to project work (PFD); `Resource.focus` (`SetResourceFocus`, `None` follows the project for people and 1.0 for machines) overrides it. It slows the rate of work: the work rules of `work.rs` run on rates, `units × focus` (`with_rates` wraps `apply_change`, `scale_units_to_work` and `spread_work`, multiplies the task's assignments' units, or an unassigned task's units by the project's factor, and puts the typed units back exactly when the rules left them alone), so 48 h of work at 1.0 units and 0.8 take 60 working hours. Units stay as typed: overallocation and leveling compare units as before. Usage rows count hours at the rate, the load map's capacity is calendar × units on the day × focus, and suggestions date each candidate at their own rate. Changing a factor (or a resource's kind) reapplies the rules as a change of units does to the leaf tasks it reaches that have not started. With every factor at 1.0 nothing is touched, so older files replay as before and `ENGINE_REVISION` did not change. MSPDI writes `units × focus` as an assignment's units (and the project's factor for an unassigned task), so Project gets the same dates; import reads every factor as 1.0. Costs follow work, so a rate is per useful hour. `FORMAT_VERSION` 24. UI: Thông tin dự án → Chung "Năng suất hữu ích" and a Năng suất column in the resource sheet (`FocusInput.tsx`, `focusPercent.ts`: "80", "80%", "0,8").
- **Importing a table** (`import.rs`, Tauri `table.rs`): `pick_table` asks for a CSV (UTF-8 with or without a mark, or UTF-16 with one; comma, semicolon or tab, taken from the first line) or a workbook (`calamine`: xlsx, xlsm, xls, xlsb, ods) and returns its first sheet as text with each row's line in the file (`lines`; blank rows are left out) (`read_table_sheet` reads another sheet of that file; the frontend never names a path). Whole numbers lose their decimal part and dates become ISO (`2026-01-05`, `2026-01-05 08:00`); at most 20,000 rows and 100 columns. The UI maps columns and converts cells; `Command::ImportRows { after_uid, resources, tasks }` carries the typed rows themselves (like `PasteTasks`), one undo step, scheduled once. People are matched by name (letter case aside): one already in the project is left as it is, new ones are added with their skills (missing skills are created); a task naming someone neither has is an error, not a new person. A task with `work` is Fixed Work (duration from the effort and its people's units; full time until someone is on it), `level` builds groups (at most one deeper than the row above; a group row takes no effort, duration or people), `values` go by field name, `after` lists rows of the import it waits for (finish to start). `build` adds rows one by one and collects every problem as a `RowError` (table, row, column, `EngineError`) instead of stopping; `check_import` (Tauri read, never logged) runs it and then `schedule` on a copy, and the command refuses with `ImportHasErrors` when anything is wrong, so a refused import changes nothing. Loops among `after` links are found with Tarjan's algorithm and reported on each row of the loop.
- **Finish forecast data** (phase 18 P4, step 4a; issue #97): a leaf task can hold an effort range for the forecast, `Task.work_low`/`work_high` (working minutes, both or neither, `0 ≤ low ≤ high`, not on summaries or milestones; `SetWorkRange`, which detaches an occurrence like other edits; the current effort may sit outside it). `Project.forecast` (`ForecastSettings`, `SetForecastSettings`) names a text or choice custom field whose tasks vary together by `group`, plus a `common` share for every task (`Strength`: none, low, medium, high → 0, 0.3, 0.5, 0.8; default medium and low); `DeleteField` and an `UpdateField` to numbers clear the field. Fill-down (`FillField::WorkRange`, leaves only), copy/paste and table import (`work_low`/`work_high`) carry the range. A leaf that later becomes a summary (a child indented under it) or a milestone (duration 0) keeps its range, and the forecast ignores ranges on summaries and milestones. A series regenerated from its recurrence builds occurrences without ranges. Scheduling never reads any of it, and MSPDI neither writes nor reads it (`.sheafly` only; an MSPDI round trip drops it silently, like the assignment rules).
- **Finish forecast** (`forecast.rs`, phase 18 P4, step 4b; a read, never logged): `forecast(project, iterations, cancel)` schedules the project and levels it when anyone is overallocated, then keeps each person's order as hidden finish-to-start links (each open leaf task waits for the earlier task of the same person that finishes last before it starts; a linked task drops leveling's delay and pauses, an unlinked one keeps them; if the links loop it goes by the user's links alone) and prepares the graph once. Each run samples every ranged leaf (not summaries, milestones, finished work, Fixed Duration tasks with people, or backwards ranges from a file) from a BetaPERT over low, today's effort clamped, high (per-task quantile tables, 257 points), scales the duration by sample ÷ today's effort (only what is left of started work; user pauses scale with it), and reruns `schedule_dates`. Correlation is a Gaussian copula: one draw for every task (`common`), one per value of the settings' field (`group`), one of the task's own, shares capped at 0.9. Every run starts from the base and has its own seed (xoshiro256** through SplitMix64, written in the engine), so the result is the same on any number of threads (`forecast_with_threads`); runs go in blocks on `std::thread::scope`, at most `MAX_ITERATIONS` (10,000), and `cancel` stops it (`EngineError::Cancelled`). The result has P50/P80/P90 per task and for the project, the share on time for each deadline, criticality, a histogram by day, `planned_finish` (as scheduled) and `leveled_finish` (the frozen base, no variation). Bench `-- forecast 500 5000 1000`: about 0.9 s on 12 threads. The Tauri read `forecast(iterations)` runs on the thread pool and answers `None` when stopped: a newer call or any document change (`mark_edited`) sets `AppState.forecast_cancel`. `api.ts` `forecast` is deliberately not queued with `inOrder`, so edits never wait a second behind it.
- **External task tracker** (phase 19, PR 1 of the pull from Backlog; issue #99; `source.rs`, `pull.rs`): `Project.source` (`SetSource`: tracker kind, site as a bare host, source project key, a filter text, hours per story point, a status map to not started / in progress / done) names the tracker; a task pulled from it holds `Task.external` (`ExternalLink`: the issue key, `synced_at`, `gone`). The engine knows no tracker and makes no network call: the Tauri layer's adapter (PR 2) turns the tracker's data into `PullTask` rows already in project units, and `Command::ApplyPull { rows, pulled_at }` carries them (one undo step; replay never touches the network). Rows are the whole result of the pull: a new key adds a task (under its parent's children when the pull names the parent, else at the end; Fixed Work from the effort; a start becomes SNET, not a manual task, so links and leveling still move it), a known key updates the linked task, a linked task whose key is missing is marked `gone` (never deleted). The source decides title, due date (deadline), start, status and the custom fields it sends, and clears a start or due date it no longer has; effort and assignee are taken only when it has one, and an assignee replaces the task's assignments at 1 unit (units set by hand stay while the person is the same); a status becomes progress (0 %, 100 %, in progress keeps a percent between 0 and 100, else 50 %); a task with children in the pull is a group and takes no effort, start, owner or progress; a task already in the project is not moved when the source changes its parent. `pull::diff` runs the same code on a copy for the preview (added / changed with the fields / same, gone, errors by row and cell); `ApplyPull` fails with `PullHasErrors` when any row is wrong and with `NothingToPull` when nothing would change, so pulling unchanged data adds no undo step and leaves `synced_at` alone. People at the source are matched by `Resource.email` (`SetResourceEmail`; unique, letter case aside; MSPDI `EmailAddress`, a repeat in a file stays with the first person). Links, the source and the pull itself live in `.sheafly` files only (MSPDI has none of them). `Project.source` is written as null when empty, because `delta.rs` copies the small project fields by hand (add a new one to `small_fields`) and a patch must be able to clear it.
- **Tracker adapter** (phase 19, PR 2; `src-tauri/src/tracker.rs`, `backlog.rs`): all network calls of a pull run in the Tauri layer, behind `Api` (a GET of a path and query answering JSON), so the adapter is tested against handwritten responses (`src-tauri/fixtures/backlog_issues.json`) and CI makes no network call. `HttpApi` (`ureq`, rustls) calls only `*.backlog.com`, `*.backlog.jp` and `*.backlogtool.com` (`is_backlog_site`: a project file naming another site cannot send a key elsewhere), over HTTPS, without following redirects, with the key in the `Backlog-API-Key` header. - **Three-way sync and conflicts** (phase 19, phase 3, PR A; `sync.rs`, `pull.rs`): a linked task remembers a `SyncBase` on its `ExternalLink`: for each synced field (`name`, `work`, `start`, `due`, `status`, `assignee`, `field:<id>`, in the canonical text of `sync::local_value`/`pull::source_value`) what the source held at the last sync (`source`) and what Sheafly held (`local`). `ApplyPull` with `resolutions` present (even empty) is a three-way pull: per field `sync::decide` compares the source's value `s`, the base and the task's value `l`: `s` unchanged since the base keeps the task however it differs (a pull no longer overwrites an edit made in Sheafly); only the source changed takes it; both changed to the same value only updates the base; both changed to different values is a conflict, listed in `PullDiff.conflicts` (`PullConflict`: base, source, local as text) and settled by `Resolution { key, field, keep }` (`Side::Source` applies the source; `Side::Sheafly` keeps the task, records the source's new value but leaves the base's local value, so the next change at the source conflicts again instead of overwriting that choice). An unresolved conflict fails the command with `PullHasConflicts`; a base updated without a task changing (`bases_changed`) still counts as a change, so a resolution is never dropped as "nothing to pull". A link with no base records one from fields that agree and reports a difference as a conflict with no base, except a start or due day a push wrote (`pushed_start/_due`). A group takes no effort, start, owner or status. New tasks of a three-way pull get a full base. `ApplyPull` without `resolutions` runs the original code (the source wins, `pushed_*` echo rule), so older logs replay as they were. `RecordPush` also moves `base.source` for the start, due and assignee written (`PushedEntry.assignee`) and leaves `base.local`, so a pull right after a push finds nothing changed; `push::plan` skips a field the source changed since the base (`PushSkipReason::SourceChanged`, `PushSkip.field`) instead of overwriting it. `FORMAT_VERSION` 19.

- **Tracking** (`tracking.rs`): actual progress follows Microsoft Project. An actual start pins the start over links, constraints, leveling, and manual dates; an actual finish pins the finish; without one the remaining work runs on from the actual start. Complete tasks (and groups) are never critical, a started task's slack is measured at its finish, and leveling skips started tasks. Remaining duration/work edits keep the done part. `late` from the status date means less is done than the schedule says is due by then (`behind_schedule`). The tracking commands live here, called from `command.rs`, including `RescheduleUncompleted` (split a started task at its progress point so the rest resumes at the status date; SNET on the status date for tasks that should have started). Recording progress on a recurring occurrence does not detach it, and regenerating a series keeps occurrences with progress. A background series (`RecurrenceSpec::background`) never sets the project finish or the critical path. EVM phases actuals over the task's segments (`evm::progress_intervals`).

Field ids are never reused (`next_field_id`), so an id the UI holds cannot come to mean another field; setting a value on a recurring occurrence detaches it, like other edits. Limits follow Microsoft Project: 30 text or choice fields (Text1–30) and 20 number fields (Number1–20). `UpdateField` converts values that still fit the new kind (and keeps renamed choices through `renamed_options`) and clears the rest. Fill-down takes a custom field (`FillField::Field`, also onto summaries), and a copy carries values by field name so a paste into another project keeps those whose field has that name there (letter case aside). `mspdi_fields.rs` writes them as `ExtendedAttribute`s: definitions before `<Calendars>`, text and choice fields in Text slots and number fields in Number slots in the order they were added, the name as `Alias`, a choice list as a `ValueList`. On import an undeclared Text/Number value makes a field named after its slot, a value missing from a list is added to it, and fields of other kinds (cost, date, duration, flag) are left out and noted in the import report, as are number values that do not read as numbers. The slot decides text or number; `CFType` (5 number, 7 text) only tells other kinds apart.
- **Split tasks** (`split.rs`): a split stores work offsets and gaps, and `leveling` when leveling made it for an urgent task (not serialized when false; a copy leaves those behind; a user split and a leveling one at the same offset stay apart and lay out as one gap); `schedule()` derives the dated `segments`. Baselines keep their own segments, and PV skips split gaps (`evm::worked_fraction`). `MoveSegment` drags segment 1 or later by setting the gap before it (later segments move along; a closed gap joins the two); segment 0 moves with the task.
- **Copy, paste, fill-down** (`clipboard.rs`): `copy_tasks` (a Tauri read, not a command) turns the selected tasks and their subtrees into a `TaskClipboard` that holds the data itself (name, relative level, duration, work, manual dates, notes, priority, calendar, constraint, deadline, task type, fixed cost, splits, assignments, links between copied tasks; not progress, baselines, leveling delay or recurrence), so `PasteTasks` replays without the originals. Paste goes after the anchor's subtree (after the whole series for an occurrence) and matches resources and calendars by UID and name, then by name. `FillDown` applies the cell's own edit command (`apply_one`) to each target in one undo step; one failing row (a cycle from predecessors) fails the whole fill.
- **Network diagram** (`network.rs`): the engine lays out the boxes and edge routes. A recurring series is one box (its summary); with summaries hidden, a link to or from a summary is drawn to the tasks that end or start the group, so an edge's `from_uid`/`to_uid` are the boxes joined, not always the link's own tasks. The `network_layout` Tauri command returns them and the UI only draws.
- **Tauri layer** (`src-tauri/src/lib.rs`): holds `Mutex<Document>`, exposes the commands wrapped by `src/api.ts`. `apply_command`, `undo`, `redo` and the large reads are `#[tauri::command(async)]`, so they run on the thread pool, not the main thread; they and the saves answer with a patch (`delta.rs`: the tasks, resources, assignments, links and usage rows that changed since the snapshot sent last, by key, plus the new order when it changed; every other project field whole; `base`/`rev` numbers) that `snapshotPatch.ts` applies to the snapshot `api.ts` holds, fetching `project_state` whole when it holds another base (after an open or anything else answered whole without a `rev`), and unchanged items and an unchanged project keep their identity; a new large `Project` list should join the patched ones. `src/api.ts` sends these one at a time (`inOrder`), and file commands wait for queued edits (`afterQueued`) without holding later calls behind their dialog. It also builds the native macOS menu from the tables in `i18n.rs` (`Entry::Submenu` groups items: File → Nhập/Xuất, Edit → Công việc (recurring, split), View → Thang thời gian, Project → Thiết lập dự án (information, custom fields, working time)/Cân bằng/Giao việc/Theo dõi (baseline, reschedule)), which sends `menu-action` events to the frontend; on macOS `menu_icons.rs` then puts an SF Symbol beside each item (found by its label in the current language, via `objc2-app-kit`, since Tauri menus take only bitmaps) after every `set_menu`. File dialogs must use the plugin's non-blocking `pick_file`/`save_file` through `await_pick`/`await_save`. `blocking_pick_file` deadlocks on the macOS main thread. The `dialog_open` flag stops two dialogs from opening at once. `apply_command`, `undo` and `redo` refuse while a dialog is open. Any command that replaces the document (new, open, import) must call `confirm_discard` while holding that permit. It asks "Lưu / Không lưu / Hủy" when there are unsaved changes. Build alerts with `alert()`, which attaches them to the main window as a sheet. Without a parent window, rfd falls back to a system notification on macOS that answered with the default button on its own when tested. Closing the window, Cmd+Q (a custom `quit` menu item, not the predefined one), and quitting from the Dock all go through `quit_if_confirmed`. **Opening files:** Open…, File → Open Recent (`recent:<index>` menu ids → `open_recent`) and files the system sends all end in `open_path_held`, after the permit and `confirm_discard`; it also records the file in the recent list (`settings.json`, ten entries, rebuilt into the menu by `refresh_menu`), as saving does. `bundle.fileAssociations` registers `.sheafly` and `.pdproj`. macOS delivers a double-clicked file as `RunEvent::Opened`; Windows and Linux pass it on the command line, and `tauri-plugin-single-instance` forwards a second launch's file to the running app. Such a file waits in `pending_open` and the frontend opens it with `open_pending` when no dialog is up (at launch, after the autosave offer).
- **Frontend** (`src/`): `types.ts` is a **hand-written mirror** of the Rust serde types, including the `Command` union. When you add or change a `Command` variant or a model field in Rust, update `types.ts` to match. `App.tsx` owns snapshot state; `menuActions.ts` (`handleMenuAction`) maps a native menu id or shortcut to its action, `useFileDialog.ts` runs one native file dialog at a time and opens a file the system sent once it is free, and `ProjectDialog`, `BaselineDialog` and `StatusBar` are their own components. ## Languages

The interface speaks Vietnamese (`vi`, the original) and English (`en`). Every user-facing string goes through a catalog; never write UI text inline.

- **Frontend** (`src/i18n/`): each area has a colocated catalog, `<Name>.i18n.ts`, made with `defineMessages(vi, en)`. `en` is typed from `vi`, so a missing key or a different function signature is a type error. Components read it with `useMessages(catalog)`; plain modules (PDF export, labels, `toolbarState`) use `pick(catalog)`, which reads the current language. Messages that take values are functions. `I18nProvider` sets the language that `format.ts` reads: Vietnamese shows `05/01/2026 08:00`, `7,5 ngày`, `3.480.000`; English shows `2026-01-05 08:00`, `7.5 days`, `3,480,000`. Parsers accept both forms in either language. Tests run in Vietnamese unless they wrap in `<I18nProvider lang="en">` or call `setCurrentLang("en")`, and must reset to `vi` afterwards.
- **Choosing the language**: `Root.tsx` loads the remembered choice (`get_language`), or follows `navigator.languages` without storing it, before the first render, and tells the backend with `set_language(lang, remember)`. View → Language (`lang-vi` / `lang-en` menu ids) switches and remembers it in `settings.json` in the app config dir (`src-tauri/src/settings.rs`).
- **Rust**: the shell's strings (menu, dialogs, alerts, About) live in `src-tauri/src/i18n.rs`; `set_language` rebuilds the native menu. The engine has `Lang` (`crates/engine/src/lang.rs`); `EngineError::message(lang)` and `OpenReport::message(lang)` give user-facing text, and `Display` stays Vietnamese. Names written into a project are data and never change with the language, so replay and saved files do not depend on it. Default names are chosen when an item is created: the UI sends localized names for new tasks, resources, milestones and calendars, and `Document::new_in(lang)` names a new project, its first task and calendar. The untouched project made at launch is renamed when `set_language` runs. Predecessor text the UI sends is normalized (`normalizePredecessorText`) to lag units the engine reads, so files stay readable by older apps. English date input accepts only ISO (`2026-01-05`).

## Third-party licenses

The installers ship `src-tauri/THIRD_PARTY_LICENSES.txt` (`bundle.resources`), and Help → Third-Party Licenses opens it (`open_third_party_licenses`). `scripts/third-party-licenses.mjs` builds it from the license files of every shipped npm package (`pnpm licenses list --prod`) and Rust crate (normal dependencies of `sheafly` on any platform, from `cargo metadata`), plus the Be Vietnam Pro OFL; a package with no license file gets the SPDX text in `scripts/license-texts/`. **Run it after adding or updating a dependency** and commit the result: CI runs it with `--check` and fails when the file is stale; it also fails when a package offers only a strong copyleft license (GPL, AGPL, …; an `OR` with a permissive choice is fine). Before adding a dependency, check its license is permissive (MIT, Apache-2.0, BSD, ISC, Zlib, Unicode, OFL for fonts; MPL-2.0 only unmodified); no GPL or AGPL.
